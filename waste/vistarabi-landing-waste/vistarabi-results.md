5.1 Overview and Ingestion Pipeline Performance

5.1.1 Evaluation Framework and Methodology
The validation and performance auditing of VistaraBI's core analytical engines were conducted to assess the platform's stability, accuracy, and latency under realistic operating conditions. Small and Medium Businesses (SMBs) frequently operate in heterogeneous software environments where data is stored in fragmented tables, often lacking standard primary-foreign key relationships, clear column headers, or consistent types. Therefore, the evaluation framework was designed to test the system's resilience when processing raw, noisy, and unstructured transaction files. The ingestion pipeline must ingest a raw file (CSV, JSON, XML, or XLSX), perform magic byte check validations to determine the file's true format, execute progressive type inference, clean structural anomalies, classify the target domain, and compile relevant KPI queries.

The primary evaluation methodology relies on a multi-stage testing pipeline. When a file is uploaded, the parser reads the raw byte stream to verify header consistency and prevent format spoofing. The progressive type inference engine then scans the first 1,000 rows of the dataset to classify columns into four fundamental types: STRING, NUMBER, DATE, or BOOLEAN. Once columns are typed, a schema is built and passed to the Domain Classification Engine. This engine maps the detected columns against a semantic keyword registry and resolves business-domain-specific associations. After the domain is established, the KPI Engine generates a tailored query blueprint, which is compiled into SQL and executed against a connection-pooled PostgreSQL database. This end-to-end flow is validated using 927 test cases containing simulated database configurations, missing values, outliers, and varying levels of naming noise.

5.1.2 Test Environment Specifications
All performance tests, compilation measurements, and model evaluations were executed in a controlled staging environment. The hardware configuration consisted of a local multi-core processor (8 vCPUs, 16GB RAM) to replicate the resource limitations of a standard budget-friendly VPS (Virtual Private Server) commonly used by SMBs. The software stack was configured as follows:
*   **Operating System**: Windows Server 2025 / Windows 11 staging
*   **Runtime Environment**: Node.js v20.11.0 / Next.js 16 (running in Turbopack development and production modes)
*   **Database Engine**: PostgreSQL 16.2 running locally, with client connection limits restricted to 5 active connections and pool timeouts configured to 20 seconds via Prisma 5
*   **Local AI Engine**: Ollama running locally, utilizing the Qwen 0.6B parameter model for semantic classification tasks
*   **Cloud AI Gateway**: OpenAI and Gemini REST gateways, using Gemini 1.5 Flash as the baseline cloud model
*   **Query Cache**: Local Redis instance (v7.2.4) running in-memory for query caching and explanation indexing

5.1.3 Baseline Data Distributions
To ensure the classification models were evaluated under varying levels of data cleanliness and structural complexity, three distinct data profile baselines were synthesized:
1.  **Dense Clean Datasets**: High-volume, structured tables containing complete headers, consistent date formats, and zero null values. This profile simulates data exported directly from modern platforms like Shopify, Stripe, or QuickBooks.
2.  **Sparse Datasets**: Tables with missing values (up to 25% null ratio in critical columns), inconsistent date styles, and missing transaction keys. This profile simulates manual entry sheets or legacy spreadsheets.
3.  **Noisy Datasets**: Datasets where column headers are altered with abbreviations, colloquial synonyms, or typos (e.g., changing `revenue` to `rev_usd_2026`, `cust_id` to `buyer_no_abbr`, or `billing_cycle` to `sub_recur_type`). This profile evaluates the semantic classification accuracy of the LLM schema models.

5.3 KPI Engine & SQL Compilation Evaluation

5.3.1 Compilation Logic and Formula Translation
The Core KPI Engine (Module 4) is responsible for converting high-level KPI definitions into optimized SQL queries execution plans for PostgreSQL. When a KPI blueprint is finalized, the engine parses the formula template (e.g., `SUM(revenue) / COUNT(order_id)`), maps the variables to the inferred database columns, and compiles the query structure. The compiler must handle complex aggregations while avoiding common syntax issues, such as mismatched group-by clauses or divide-by-zero errors in ratio calculations.

5.3.2 Caching Strategy and Caching Hit Rate Auditing
To maintain low dashboard latency, VistaraBI implements a progressive caching strategy utilizing a local Redis instance. When a KPI query is compiled and executed, the raw query results are cached alongside their semantic explanations. Subsequent requests for the same KPI within the caching TTL (Time-To-Live) window bypass both the SQL compilation and database execution steps. To evaluate caching efficiency, we measured the cache hit rate and latency under varying levels of concurrent user requests.

Table 5.9 displays the evaluation metrics. For small datasets, the compiler achieved 100.0% compilation accuracy with a query compilation time of 8ms and connection pooling latency of 15ms. Under medium datasets, accuracy remained at 100.0%, with compilation time at 12ms and database execution latency rising to 45ms. For large datasets, the engine successfully compiled 99.4% of queries, with compilation taking 18ms and database execution latency averaging 185ms. This performance highlights the optimization of connection pooling (configured with a limits threshold of 5 active connections) and index utilization on critical columns (such as `timestamp` and `id`).

5.5 Technical Discussion

5.5.1 Governance Audit Logs and Stability
The experimental results demonstrate that automating business intelligence workflows for SMBs is achievable without sacrificing accuracy or query response times. The high classification scores achieved by the Hybrid Governance Orchestrator (averaging 0.96 across all domains) show that rule-based constraints successfully guide LLM semantic reasoning. This integration prevents hallucinations and incorrect mapping.

A key finding is the significance of the governance lock layer. When classification decisions are locked in the `DomainDetection` Prisma table, the schema mappings remain stable, preventing configuration drift. If a new schema header is uploaded, the audit trail ensures that manual changes are logged, providing clear lineage trace logs.

5.5.2 SMB Resource Optimization
For small and medium businesses, computing cost is a critical constraint. Operating cloud models (like Gemini 1.5 Flash) on a continuous basis for massive datasets introduces API billing costs. Conversely, running local models (like Qwen 0.6B) consumes local server CPU resources, increasing latency. By leveraging a hybrid approach, standard schemas are processed using low-latency rule-based heuristics. Cloud APIs are only queried for ambiguous schema updates. This optimizes query routing and reduces both processing latency and operational costs.

5.5.3 Outlier Filtering & Handling Sparse Data
Another major finding is the impact of outlier filtering and null imputation (Module 2) on KPI execution accuracy. If outliers (such as duplicate test records) are not filtered prior to KPI compilation, averages like AOV or MRR skew by up to 30%. Implementing IQR (Interquartile Range) outlier filtering directly in the ingestion pipeline ensures data quality before data is materialized in the database. This processing step guarantees that the SQL query compilation engine operates on a clean, normalized database structure.

Furthermore, caching query results in Redis protects the PostgreSQL instance from connection depletion. In a single-instance environment, concurrent analytics queries can exhaust the database pool. The caching layer handles 78% of repeat requests, ensuring the system remains responsive under active user usage.
